本次验收从本机已安装的 Barn 1.0.0 出发，安装公开的 1.1.0 Homebrew 配方，验证升级与日常使用，再重建测试环境。**剧本先于执行编写；本轮已结束，主要功能通过，发现一项恢复问题，另有剪贴板与宿主提权检查未完成。** 已获授权删除本机现有 Barn 虚拟机。

## 环境与证据 {#environment}

- 宿主：macOS 27.0.1、Apple Silicon、18 个逻辑 CPU、128 GiB 内存；QEMU 11.1.3。
- 初始环境：8 台运行中的 Linux VM 与 1 台运行中的 macOS VM `mac1`；正常安装路径为 `/opt/homebrew/bin/barn`。
- 升级对象：公开版本 `v1.1.0`，提交 `b2cc8da8983e710255d504bf26bf5d7b3f182790`。
- 录像、原始输出、断言结果与执行脚本保存在仓库外的独立验收目录。每阶段产生一个 asciicast v2 文件，保留原始时间轴，并生成限制等待时长的观看版本。
- Linux 验收使用真实用户的 `~/.barn`。原生 Mac 深度验收复用源码中的 `tests/mac-live-acceptance.py`，使用专用测试数据目录及已有基础镜像的 APFS 克隆；最后验证正常用户路径。
- 终端录像不采集键盘输入、不输出密码或 SSH 私钥。桌面通过原生应用界面验收，截图在本次验收聊天中；剪贴板结果见下文。

## 判定与重试 {#criteria}

每条命令记录参数、退出码、耗时与原始输出。断言失败立即保留现场；修正剧本错误后另起重试记录，产品缺陷单独记录，不把失败片段从录像中删去。长等待只在观看副本中加速，原始记录保留。

已有宿主网络先通过只读检查与复用路径验证。需要宿主 sudo 的安装、卸载或 hosts 操作先检查实际授权与执行计划；不能完成的项目明确标记阻塞。Apple 系统镜像更新、Intel Mac 实机与 Linux KVM 属于其他环境的验收范围。

### 强制终止后的就绪标记问题 {#recovery-gap}

在 Ubuntu 24.04 arm64/HVF 节点重建成功后立即强制终止 QEMU，随后 `up` 启动了客机，但 `/var/lib/barn/ready.json` 与 `error.json` 均不存在。SSH 和持久数据可用，cloud-init 已结束，`up` 等待 180 秒后以退出码 `5` 失败。这是本轮实际观察到的一项恢复缺口，记录在 `03-linux-lifecycle-r3` 与 `03-power-loss-investigation`。

本次通过以下操作恢复就绪状态，运行中的 VM PID、对端节点和持久数据均保留：

```bash
barn exec meta -- sudo -n /usr/local/libexec/barn-finalize
barn up meta -f barn.yml
```

再次试验时先在客机执行 `sudo sync`，再核对 QEMU 命令行和 QMP UUID 后强制终止；这次 `up` 自动恢复成功。立即断电的现象仅在上述条件下观察到一次，落盘时机与其他镜像的表现仍需进一步定位。代码依据为 1.1.0 的 [就绪探测](https://github.com/pgsty/barn/blob/v1.1.0/internal/vm/lifecycle.go#L584) 和 [初始化重试入口](https://github.com/pgsty/barn/blob/v1.1.0/internal/private/start.go#L162)。
