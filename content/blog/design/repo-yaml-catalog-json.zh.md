本文介绍 Barn 0.9.0 的 Linux 镜像仓库。macOS 安装镜像由
[Mac 命令](/zh/docs/reference/mac/)单独管理。

静态镜像仓库包含 qcow2 文件和 JSON 索引，但并非所有元数据都适合手工维护。手工复制校验和与大小容易出错，而将策略埋在生成的 JSON 中，又会让通道变化与版本弃用难以审查。

因此，Barn 将维护者定义的策略与工具从发布文件中计算的事实分开。

## `repo.yaml`：维护者表达什么意图

纳入版本控制的 `repo.yaml` 定义镜像策略：

- 仓库修订号与默认选择；
- 镜像系列与别名；
- `stable` 等可移动通道；
- 精确版本与架构；
- 启动模式与支持状态；
- 不可变上游与来源记录说明。

该文件不包含生成的镜像文件大小、SHA-256 或虚拟磁盘容量。一条配置可以将
`d13:stable` 映射到某个准确版本，并提供 amd64/arm64 架构变体。工具另行计算文件元数据。
下面的策略片段演示格式；完整可用示例见[镜像仓库](/zh/docs/start/images/)，
当前版本以镜像参考为准：

```yaml
defaults: { image: d13, channel: stable, arch: native, boot: uefi }
images:
  d13:
    aliases: [debian13, debian, trixie]
    channels: { stable: "20260810.2566.0" }
    versions:
      "20260810.2566.0":
        status: supported
        variants:
          amd64: {}
          arm64: {}
```

拉取请求可以直接在策略文件中展示通道变化、版本弃用与来源说明的修改。

> [!NOTE]
> 仓库语法与客户端行为见[镜像参考](/zh/docs/reference/images/)，
> 候选镜像准备属于独立的[镜像流水线契约](/zh/docs/reference/image-pipeline/)。

## `catalog.json`：仓库能够证明什么

`catalog.json` 记录策略对应的镜像文件。每个架构变体都包含准确文件名、字节数、SHA-256、
qcow2 虚拟磁盘容量、启动约定、源镜像用户与不可变上游的来源记录。

工具从文件中取得文件名、字节数、摘要与虚拟大小，并检查这些值。启动模式、源用户、状态与来源记录取自
`repo.yaml` 中经过校验的策略。文件检查本身不能证明这些策略声明。
构建会解析 qcow2，拒绝后端镜像文件、外部数据、加密与未知不兼容特性。结构检查通过后，工具才原子替换镜像目录。

文件身份是 `(image, exact version, architecture)` 三元组，而不是选择它的通道。
文件保持可读、不可变的名字：

```text
images/d13-20260810.2566.0-arm64.qcow2
```

可读文件名让管理员能够使用标准文件系统工具检查、镜像或恢复仓库。生成的元数据与验证过程保证完整性，文件名本身不能证明完整性。

## 三个操作，三种职责

仓库 CLI 把观察、生成与证明分开：

| 命令 | 职责 |
| --- | --- |
| `barn repo scan` | 只读报告已跟踪、缺失、未跟踪与不安全文件 |
| `barn repo build` | 校验仓库定义与镜像文件，再原子生成镜像目录 |
| `barn repo verify` | 在内存中重新生成镜像目录，并要求与已发布目录逐字节一致 |

`build` 永远不修改 `repo.yaml` 或 qcow2 字节。`verify` 比“每个校验和都正确”更强：它还能
确认生成的镜像目录没有遗漏仓库定义或镜像文件的任何变化。

先上传不可变镜像文件，最后发布镜像目录与匹配签名，并尽量一起切换这两个文件。
上传未完成导致正文与签名不匹配时，客户端会拒绝该组合。先上传镜像可以防止镜像目录发布尚不可用的下载。

## 选择器可以移动，文件不能

人工配置需要方便的选择器。随着仓库演进，`d13:stable`、`el9@9` 与 `el9@9.7` 可以解析到
更新的准确版本。数字前缀按点分组件的整数比较，因此 9.10 排在 9.9 之后。

解析完成后，客户端保存准确版本、架构、大小与摘要。通道变化不会改变已经解析的节点。
选择器可以在选择阶段变化，执行阶段则使用已记录的不可变身份。

## 传输与信任是两个问题

官方镜像目录与普通 HTTP 镜像目录必须具有受信分离式签名。操作者可以显式选择使用未签名镜像目录的本地目录或 HTTPS 仓库，以此信任本地属主或认证传输。隐式使用编译时默认仓库仍需遵守签名策略，即使 URL 使用 HTTPS。

Barn 按仓库独立记录已接受的镜像目录状态。它拒绝未知密钥、低于最高已接受值的修订号，以及相同修订号对应不同字节的情况。
显式降级只影响选定仓库。重置到内置镜像目录仍会保留防回滚记录。

接受镜像目录后，每次拉取仍会检查字节数、SHA-256 与 qcow2 结构。通过验证的基础镜像变为只读，节点根盘则使用可写的写时复制层。因此，普通虚拟机写入不会修改受信基础镜像。

## 不同信任域保持分离

镜像目录通过 Minisign 签名认证镜像策略；应用发布提供 `checksums.txt`，用于核对下载文件，
当前工作流不生成独立的应用发布签名或来源证明包。原生 Mac 应用的 Developer ID 签名
与公证又是另一条流程。这些机制各有用途，不能用应用校验和替代镜像目录签名。

Barn 发布版本默认使用 `https://repo.pigsty.io/barn`，并通过 `--mirror` 显式选择
`https://repo.pigsty.cc/barn`；`--repo` 仍是自定义覆盖。两个
官方仓库在下载镜像时可以互相回退，始终校验同一镜像目录的尺寸与 SHA-256。自定义仓库
仍是唯一产物源，镜像目录更新仍使用选定来源；内置镜像目录的上游 URL
只提供溯源，绝不会变成产物回退。源码配置、生成
镜像目录、上传文件、签名与公开可用性仍是彼此独立的发布门禁。

维护者应能直接审查策略。工具应生成已发布文件的元数据，确保这些事实可复现，并能独立验证。
